# 迁移路线

> 状态：第一轮 feature 已定为 **F2 工具循环**（2026-11-03）。F0/F1 是它的前置子步骤，不再单独作为一轮。其余 feature 仍是候选，按讨论顺序推进。

## 1. 原则

- 每个 feature 必须能独立编译、运行、测试。
- 先抄最靠近该 feature 的 codex 代码，缺的接口用最小实现补。
- 每个 feature 一个 commit，结束时更新本文与 [决策记录](06-决策记录.md)。
- 不按 crate 大小排序，按“能否尽快验证关键假设”排序。

## 2. 候选 feature

| 编号 | 候选 | 验证的核心假设 | 依赖 | 状态 |
|---|---|---|---|---|
| F0 | workspace + 协议/配置底座 | 目录结构与 `rsi-core-*` 命名能立住 | 无 | F2 子步骤 |
| F1 | 单轮流式模型调用 | 网关的 `/responses`、SSE、usage 可用 | F0 | F2 子步骤 |
| F2 | 工具循环 + 原生工具 | function call、工具结果回传、多轮可用 | F1 | **第一轮，进行中** |
| F3 | 会话/上下文/压缩 | 长会话、token 账本、压缩可用 | F2 | 候选 |
| F4 | 执行环境与沙箱 | 工作区边界、命令执行、超时/输出截断 | F2/F3 | 候选 |
| F5 | MCP + hooks | 框架能注入证据查询/实验工具；钩子可审计 | F2 | 候选 |
| F6 | job 描述 + 预算 + 结构化输出 | 内核能作为子进程被框架调用 | F1-F5 | 候选 |

## 3. 各候选的范围与验收

### F0 workspace + 协议/配置底座

**范围**

- 建 Cargo workspace、`rust-toolchain.toml`、`rustfmt.toml`、`.gitignore`、`LICENSE`/`NOTICE`。
- 建 `rsi-core-protocol`、`rsi-core-model-provider-info`、`rsi-core` 的最小骨架。
- 抄 `ResponseItem`/`ContentItem`/`TokenUsage` 子集；写配置解析与单测。
- 不联网。

**验收**

- `cargo test` 全绿。
- 配置示例能解析成 provider/model 结构。
- `ResponseItem` 的 JSON 序列化/反序列化与 codex fixture 一致。

**风险**

- 只搬类型，暂时看不到端到端效果；容易过度设计。

### F1 单轮流式模型调用

**范围**

- `rsi exec --prompt "..."`：读配置，发一次 `/responses`，流式打印文本。
- 打印 response id、usage、耗时；错误带 HTTP 状态/SSE 事件。
- `--json` 输出解析后的事件。
- mock HTTP + SSE fixture 测试。
- 真实网关 smoke（需 `LLM_API_KEY`）。
- 用 dummy function tool 探测网关是否接受 `tools`（只打印，不执行）。

**验收**

- mock 下文本流、usage、401/500/断流/畸形事件都有测试。
- 真实网关 smoke 成功。
- 不依赖 codex 的 auth/telemetry/websocket。

**风险**

- 网关行为与 OpenAI Responses 不完全一致；需要按实际响应调整。
- `codex-api` 的 Request 构造依赖 `protocol` 较多；子集边界要切准。

### F2 工具循环 + 原生工具（第一轮）

**范围**

- 先完成 F0/F1：workspace、配置、provider、Responses 流式客户端。
- `ResponseItem` 的 function/custom tool call、function_call_output。
- 工具注册表、工具描述、路由、串行/并发策略。
- 先做 2-3 个工具：`read_file`、`shell`、`apply_patch`（工具面按讨论结果定）。
- 多轮循环：模型调用 → 工具 → 结果回写 → 再调用，直到无工具或预算。
- 最小 JSONL 事件（工具调用/结果/用量），先作为调试输出，schema 可演进。
- 最简终端前端：`rsi exec` 一次性执行 + `rsi chat` REPL；纯 stdout/stderr，不做 TUI，后续可删。

**验收**

- 模型能读文件、跑命令（以及改文件，如果本轮包含 `apply_patch`），完成一个多步任务。
- 工具错误/超时/输出截断不会中断会话。
- 工具面按配置暴露；未暴露的工具模型看不到。
- 终端能清楚看到文本流、工具调用、工具结果、usage、错误。
- mock SSE 测试覆盖：纯文本、function_call、多轮、工具错误、预算终止。

**风险**

- `apply_patch` 与 shell 的权限/路径边界；沙箱可能要先做最小版。
- 工具结果格式与模型预期不一致，容易多轮空转。
- 网关对 `custom` 类型工具的支持未知；`apply_patch` 可能先以 function 工具暴露。

### F3 会话/上下文/压缩

**范围**

- 系统提示/开发者提示装配；AGENTS.md 是否需要（待定）。
- 历史、token 估算、上下文窗口。
- 自动压缩（摘要）与手动压缩。
- token 账本：input/cached/output/reasoning。

**验收**

- 长会话不超上下文；压缩后任务能继续。
- usage 账本与网关返回一致。
- 压缩事件可观测。

**风险**

- 压缩质量影响任务成功率；需要真实任务验证。
- codex 的 compact 代码与 remote compaction/多模型耦合，子集要切。

### F4 执行环境与沙箱

**范围**

- 工作区边界：路径规范化、符号链接、读写限制。
- 命令执行：超时、输出截断、后台进程、PTY（按需）。
- 命令策略：危险命令、白名单、只读阶段。
- 沙箱：容器边界 vs Landlock；先做哪一种待定。

**验收**

- 工作区外读写被拒绝。
- 命令超时/大量输出/异常退出可诊断。
- 只读阶段拿不到写工具/写权限。

**风险**

- `exec-server` 体量大；直接用 `std::process` 可能更快，但后续补 RPC/远端会重构。
- 沙箱在 macOS 开发机与 Linux 容器行为不同。

### F5 MCP + hooks

**范围**

- MCP 客户端连接、工具发现、调用、超时、token。
- MCP 工具转 Responses 工具描述。
- 工具前后 hooks：审计、预算、脱敏、阶段提示。
- 动态工具注入。

**验收**

- 框架能通过 MCP 注入一个证据查询工具并被模型调用。
- hook 能在工具调用前后记录/阻断。

**风险**

- `rmcp-client` 很大；先只支持一种传输。
- MCP server 本身还没写（属于 rsi 框架），需要 mock server 测试。

### F6 job 描述 + 预算 + 结构化输出

**范围**

- `rsi run --job job.json`。
- job 解析/校验；工具面/模型/预算/workspace/output/events。
- 预算执行与终止事件。
- output_schema 校验与写出。
- 退出码约定。

**验收**

- 框架侧给一份 job，内核能独立跑完并写出事件/输出。
- 预算超限返回部分结果与明确原因。
- 输出不符合 schema 时失败可诊断。

**风险**

- job schema 与 rsi 框架耦合；需要先定契约。
- 事件 schema 一旦稳定，改动成本高。

### F7 事件流 + 持久化/恢复

**范围**

- 稳定 JSONL 事件 schema。
- 会话恢复/断点续跑（如果需要）。
- 与面板/证据库/成本核算的字段对齐。
- 崩溃恢复：已写事件可读，未完成会话可标记。

**验收**

- 一次会话的事件能被独立工具解析。
- 恢复后能继续未完成回合（如果决定做）。
- 事件字段有版本号/兼容策略。

**风险**

- 复用 codex `rollout` 会拖入 `thread-store`/`state`；自建更轻但要做恢复逻辑。
- 事件过多会影响性能/存储。

### F8 配置/CLI/清理/发布

**范围**

- 配置分层、profile、provider 覆盖、环境变量。
- CLI 体验、日志、错误信息。
- 删除不再需要的 codex 代码/feature flag。
- 构建/发布脚本、容器镜像、CI。

**验收**

- `rsi --help`/`rsi doctor` 可用。
- 干净环境能构建/运行。
- 仓库里没有未使用的 codex 子系统。

## 4. 第一个 feature 的讨论清单

逐项确认：

1. 先做 F0+F1（模型链路），还是直接 F2（工具循环）？
2. 是否接受“先 mock、再真实网关”的调试顺序？
3. 事件是先做最小 JSONL，还是等 F7 再统一？
4. 工具循环前是否必须先有沙箱/路径边界？
5. 是否保留 codex 的 `ResponseItem` 命名与 JSON 形状，还是改成 rsi 自有？
6. 第一版 CLI 是 `rsi exec` 还是直接 `rsi run --job`？

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| codex 工作区在变 | 复制到一半的代码与快照不一致 | 每次记录 commit/快照；必要时让 codex 先冻结 |
| `core` 耦合深 | 子集编译不过，越补越多 | 从 `codex-api`/`codex-client` 低层开始；缺的接口用最小实现 |
| 网关行为未知 | F1/F2 可能返工 | 先做 streaming/tool/reasoning 探测 |
| 测试缺失 | 后续改动容易回归 | 每个 feature 带 mock/fixture 测试 |
| 过度设计 | 事件/job schema 反复改 | 先最小可用，标记版本，后续兼容 |
| 许可证/归属 | 合规问题 | 根目录 `LICENSE`/`NOTICE`，保留来源说明 |
