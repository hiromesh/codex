# 模型调用链路笔记

这是模型链路的技术底稿。原 F1 已并入第一轮 F2 工具循环，作为 F2 的第一步；用来回答：抄哪些文件、怎么拼、怎么测、网关要验什么。

## 1. 为什么先看这条链路

后面所有 feature（工具循环、会话、压缩、MCP、预算）都建立在“能稳定地和模型完成一次流式请求”上。设计文档 §6.4 还留了四个待验证项：

1. 流式事件是否按 Responses 规范返回；
2. `function` 类型工具是否被网关接受；
3. 工具调用结果回传是否正常；
4. reasoning item 的行为。

先用最小代码把这条链路跑通，比先搭一个空框架更有价值。

## 2. codex 的调用链

```text
core::session::turn::run_turn
  -> core::client::ModelClientSession::stream
  -> core::client::ResponsesHttpExecutor::stream_responses_http
  -> codex_api::ResponsesClient::stream_request
  -> codex_api::endpoint::session::EndpointSession
  -> codex_client::Provider + RetryPolicy + HttpTransport
  -> codex_http_client::HttpClient (reqwest)
  -> POST {base_url}/responses
  -> SSE
  -> codex_api::sse::spawn_response_stream
  -> codex_api::sse::responses::process_responses_event
  -> codex_api::ResponseEvent
  -> core 回合循环
```

对应文件：

| 层 | 文件 | 说明 |
|---|---|---|
| core 采样 | `core/src/session/turn.rs` | 回合循环、工具调度、压缩 |
| core 客户端 | `core/src/client.rs` | `ModelClient`/`ModelClientSession`、auth、telemetry、websocket、重试 |
| API 请求 | `codex-api/src/common.rs` | `ResponsesApiRequest`、`ResponseEvent` |
| API 端点 | `codex-api/src/endpoint/responses.rs` | `ResponsesClient::stream_request` |
| 传输会话 | `codex-api/src/endpoint/session.rs` | `EndpointSession`：重试、auth、telemetry |
| SSE | `codex-api/src/sse/responses.rs` | `process_responses_event`、`spawn_response_stream` |
| 通用客户端 | `codex-client/src/{provider,retry,sse}.rs` | `Provider`、`RetryPolicy`、SSE 转发 |
| HTTP | `codex-http-client/src/{request,response,transport,client,error}.rs` | reqwest/TLS/代理/网络策略 |

### 2.1 四层职责与目录位置

codex 的这几层都在 `codex-rs/` 下，不在仓库根目录。我们的目录层级与 codex 一致，目录名和包名按 D-002 用 `rsi-core-*`：

| 层 | codex 目录（包名） | rsi-core 目录（包名） | 职责 | 不知道什么 |
|---|---|---|---|---|
| HTTP 传输 | `http-client/`（`codex-http-client`） | `rsi-core-http-client/`（`rsi-core-http-client`） | reqwest 封装、request/response 类型、TLS/自定义 CA、代理/路由、流式 body | 不知道 OpenAI/Responses |
| 通用客户端 | `codex-client/`（`codex-client`） | `rsi-core-client/`（`rsi-core-client`） | `Provider`、重试策略、通用 SSE 转发、请求 telemetry | 不知道 Responses 事件 |
| API 协议 | `codex-api/`（`codex-api`） | `rsi-core-api/`（`rsi-core-api`） | `/responses` 请求构造、SSE 事件解析、错误映射、auth header | 不知道会话/工具循环 |
| 供应商配置 | `model-provider-info/`（`codex-model-provider-info`） | `rsi-core-model-provider-info/`（`rsi-core-model-provider-info`） | provider 定义、`WireApi`、env key、base URL、重试/超时 | 不发起请求 |
| 会话循环 | `core/`（`codex-core`） | `rsi-core/`（`rsi-core`） | 回合、工具、压缩、上下文；通过 `ModelClient` 用 API 层 | 不直接碰 reqwest |

为什么这样拆：

- 换传输（代理、CA、TLS 后端）不该改 SSE 解析；改 Responses 事件也不该碰 reqwest。
- 使用真实网关验证传输与错误路径，使用真实服务产生的事件验证 SSE 解析。
- 和 codex 边界一致，后续抄 `RetryPolicy`、proxy、custom CA 时不用重构。
- 第一刀里 `rsi-core-http-client` 只有 74 行、`rsi-core-api` 417 行；看起来“多”，但都是薄层，后面会长。

codex 的 `codex-api` 还包含图片生成、搜索、记忆、实时会话与 WebSocket 接口。模型通信、网页搜索和记忆使用的接口按对应功能迁移；图片生成与编辑功能移除。

关键点：

- `core/src/client.rs` 有 3271 行，和 auth/telemetry/websocket/extension 深度耦合。F1 不要直接抄它，直接用 `codex-api::ResponsesClient`。
- `codex-api` 的模块大多是 `pub(crate)`；拆成独立 `rsi-core-api` crate 时，需要把对外用的类型/函数改成 `pub`，或者保留一层 `lib.rs` facade。
- `codex-client` 只有 300 行，整块抄成本很低。
- `codex-http-client` 有 11.8k 行（含测试），代理/路由/ChatGPT 头/自定义 CA 很多；F1 只抄最小传输，其他后置。

## 3. 请求

`ResponsesApiRequest` 的字段（按序列化顺序）：

```rust
pub struct ResponsesApiRequest {
    pub model: String,
    pub stream: bool,
    pub service_tier: Option<String>,
    pub input: Vec<ResponseItem>,
    pub tools: Option<ResponsesApiTools>,
    pub tool_choice: String,
    pub parallel_tool_calls: bool,
    pub reasoning: Option<Reasoning>,
    pub store: bool,
    pub stream_options: Option<StreamOptions>,
    pub include: Vec<String>,
    pub prompt_cache_key: Option<String>,
    pub text: Option<TextControls>,
    pub client_metadata: Option<HashMap<String, String>>,
    pub access_programs: Option<AccessPrograms>,
}
```

codex 不把 base instructions 放在顶层 `instructions` 字段；它在 `input` 最前面插入一条 `role: "developer"` 的 message，内容为 `BaseInstructions`，后面才是对话历史。

F1 的最小请求：

```jsonc
{
  "model": "deepseek-flash",
  "stream": true,
  "input": [
    {
      "type": "message",
      "role": "user",
      "content": [{"type": "input_text", "text": "用一句话介绍你自己"}]
    }
  ],
  "tools": [],
  "tool_choice": "auto",
  "parallel_tool_calls": false,
  "reasoning": null,
  "store": false,
  "include": []
}
```

注意：

- `input` 的每一项是 `ResponseItem`，`type` 用 snake_case。
- 用户文本是 `input_text`；助手输出文本是 `output_text`。
- `tools` 为空时，codex 仍会传 `[]`（`Option` 有值）；也可以省略。网关对两种写法的接受度要测。
- `reasoning` 为 `None` 时会序列化成 `null`；如果网关不接受，改成 skip。
- `store=false` 不把会话存在模型侧；RSI 的证据由自己落盘。

## 4. SSE 事件

codex 的 `process_responses_event` 处理这些事件：

| SSE `type` | 映射 |
|---|---|
| `response.created` | `ResponseEvent::Created` |
| `response.output_item.added` | `OutputItemAdded` |
| `response.output_text.delta` | `OutputTextDelta` |
| `response.output_item.done` | `OutputItemDone`（完整 item，含 function_call） |
| `response.reasoning_summary_text.delta` | `ReasoningSummaryDelta` |
| `response.reasoning_summary_text.done` | `ReasoningSummaryDone` |
| `response.reasoning_text.delta` | `ReasoningContentDelta` |
| `response.reasoning_summary_part.added` | `ReasoningSummaryPartAdded` |
| `response.completed` / `response.incomplete` | `Completed`（含 usage、end_turn） |
| `response.failed` | 错误 |
| `error` | 错误 |
| `response.function_call_arguments.delta/done` | codex 当前忽略，依赖 `output_item.done` 的完整 item |
| `response.output_text.done`、`response.content_part.*` 等 | 忽略 |

F1 要做的：

- 解析 `output_text.delta` 流式打印。
- 在 `output_item.done` 里识别 `function_call`，打印 name/arguments（不执行）。
- 在 `completed` 里取 `usage`（input/cached/output/reasoning/total）和 `response_id`。
- 在 `error`/`response.failed` 里映射成可读错误（HTTP 状态、provider error code、message）。

## 5. 错误、重试、超时

codex 的分层：

- `codex-client::RetryPolicy`：429/5xx/传输错误的重试与退避。
- `codex-api::ApiError`：HTTP/SSE/解析错误。
- `codex-api::sse`：SSE idle timeout（`Provider::stream_idle_timeout`，默认 300s）。
- `core/src/responses_retry.rs`：流中断后的重连/续传（F1 不做）。

F1 最小策略：

- 连接失败/429/5xx：按 `RetryConfig` 重试 2-3 次，指数退避。
- SSE 超时：报错退出，保留已输出文本。
- 畸形事件：跳过并记录，不 panic；连续多次畸形则失败。
- 401/403：不重试，提示检查 `LLM_API_KEY`。

## 6. Provider 配置

```toml
model = "deepseek-flash"
model_provider = "gateway"

[model_providers.gateway]
name = "leihuo"
base_url = "https://ai-idc-inner.leihuo.netease.com/v1"
env_key = "LLM_API_KEY"
wire_api = "responses"
```

F1 只需要这些字段：

- `name`
- `base_url`
- `env_key`（或 `experimental_bearer_token`，不推荐）
- `wire_api`（只接受 `responses`）
- `request_max_retries` / `stream_max_retries` / `stream_idle_timeout_ms`
- `http_headers` / `env_http_headers`
- `query_params`

`model-provider-info` 里的 AWS/GCP/OAuth/模型目录/capabilities 先不抄。

## 8. crate 结构

```text
rsi-core/
  rsi-core-rs/                  # Rust workspace
    Cargo.toml
    rust-toolchain.toml
    rustfmt.toml
    rsi-core-protocol/          # ResponseItem 子集、TokenUsage
    rsi-core-client/            # Provider、重试、SSE 转发
    rsi-core-http-client/       # reqwest 最小传输
    rsi-core-api/               # Responses 请求与 SSE 解析
    rsi-core-model-provider-info/
    rsi-core/                   # config + Conversation
    rsi-core-cli/               # exec / chat，二进制 rsi-core
```

目录层级与 codex 一致；目录名、包名用 `rsi-core-*`，导入用 `rsi_core_*`。这符合 [D-002](06-决策记录.md#d-002-工作区与-crate-命名用-rsi-core-)。

## 9. 测试方案

### 9.1 单测

- `ResponseItem`/`ContentItem` 的 JSON 序列化/反序列化 fixture。
- `process_responses_event` 对每种 SSE 事件的处理。
- 错误映射：HTTP 401/403/429/500，SSE `error`，`response.failed`。
- 配置解析：缺 env、非法 wire_api、默认重试值。

### 9.2 协议数据验证

- 使用真实服务返回的事件记录验证 SSE 与 JSON 解析。
- 通过真实服务验证认证错误、服务错误、断流和超时。
- 检查实际请求中的 model、stream、input 和 tools。

### 9.3 真实网关 smoke

需要 `LLM_API_KEY`。步骤：

1. 纯文本：流式输出、usage、response_id。
2. 调用实际注册的工具：确认网关接受 `tools`，返回 `function_call`。
3. 工具结果回传：发 `function_call_output`，确认模型继续。
4. reasoning：确认 reasoning item 是否返回、是否需要回传。
5. 错误：错误 key、错误 model、超时。

smoke 脚本不把 key 写进仓库；用环境变量。

## 10. 网关验证清单

| 项 | 问题 | 影响 |
|---|---|---|
| 流式 | 是否支持 `stream:true` + SSE | F1 基础 |
| 事件名 | 是否与 OpenAI Responses 一致 | 解析器是否需要兼容层 |
| usage | `response.completed` 是否带 usage | 成本核算 |
| 工具 | `tools` 是否接受 function 类型 | F2 基础 |
| 工具回传 | `function_call_output` 是否接受 | F2 多轮 |
| reasoning | reasoning item 是否返回/可回传 | 上下文/压缩 |
| `store` | 是否接受 `store:false` | 隐私/会话 |
| `include` | 空数组/未知值是否报错 | 兼容性 |
| `reasoning` | `null` 是否接受 | 请求构造 |
| 错误格式 | HTTP/SSE 错误结构 | 错误映射 |
| 超时 | 空闲连接/长响应行为 | 重试策略 |
| 压缩 | 是否支持 gzip/zstd 请求体 | 大上下文 |

## 11. 不在 F1 范围

- 工具执行与多轮循环。
- 会话历史、上下文压缩、token 预算。
- 沙箱、权限、exec-server。
- MCP、hooks。
- 事件 schema 的最终形态。
- 持久化/恢复。
- websocket 传输（gateway 大概率只有 HTTP SSE）。

## 12. 风险

- 网关不是标准 Responses：可能需要适配层。先探测，再决定是否写兼容代码。
- `codex-api` 的 `pub(crate)` 边界：拆 crate 时要调整可见性，容易引入大 diff。
- `protocol` 子集越抄越大：`ResponseItem` 的变体互相引用；F1 只留 Message/FunctionCall/FunctionCallOutput/Reasoning，其他用 `serde_json::Value` 兜底或后补。
- 真实网关的流式事件顺序/字段可能与 codex fixture 不同：fixture 要来自真实录制，不要手写。
