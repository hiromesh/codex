# 内核契约

目标契约，来自 [RSI 平台设计讨论](/Users/hiro/ugc-platform/docs/rsi/RSI平台设计讨论.md) §6/§7，以及当前项目决策。标“草案”的部分还没最终确认。

## 1. Job 描述

内核按 job 启动，一次进程、一次会话。草案字段（设计文档 §6.3）：

```jsonc
{
  "stage": "diagnose",
  "system_prompt_file": "/run/jobs/1001/system.md",
  "workspace": "/work/ugc-platform",
  "tools": {
    "native": ["read_file", "apply_patch", "grep"],
    "mcp": [
      {"name": "rsi", "url": "http://127.0.0.1:8100/mcp", "token": "..."}
    ]
  },
  "model": {"provider": "gateway", "name": "deepseek-flash"},
  "budget": {
    "max_turns": 40,
    "max_input_tokens": 400000,
    "deadline_s": 1800
  },
  "output_schema": "/run/jobs/1001/output.schema.json",
  "events": "/run/events/1001.jsonl"
}
```

待定字段：

- `output_path`：结构化输出写到哪里（stdout / 文件）。
- `reasoning_effort` / `service_tier`：模型参数是否由 job 指定。
- `max_output_tokens` / `max_tool_calls`：预算是否细分。
- `env`：是否允许 job 注入环境变量。
- `metadata`：交给事件流的标签（周期 id、候选 id 等）。

## 2. 硬约束

设计文档 §6.3 的三条，必须由代码保证：

1. **工具面由 job 指定**。没有 shell 的阶段拿不到 shell；没有写权限的阶段拿不到 `apply_patch`。
2. **工作区外的路径不可读写**。沙箱在容器内生效。
3. **预算到点直接终止**，返回已产生的事件与失败原因。

补充约束（草案）：

4. 无人在环：不出现审批、提问、权限申请类工具。
5. 不依赖 codex 云端：认证只走 `env_key`，遥测不落外部服务。
6. 事件只追加，不修改；崩溃后已写事件仍可读。

## 3. 工具面

### 3.1 原生工具

第一期候选：

| 工具 | 用途 | 备注 |
|---|---|---|
| `read_file` | 读文件 | 需要路径边界与大小限制 |
| `apply_patch` | 改文件 | 只允许工作区内；冻结路径由框架校验 |
| `shell` / `exec` | 跑命令 | 只在 job 允许时暴露；命令策略/超时/输出截断 |
| `grep` / `glob` | 搜索 | 证据检索与代码定位 |
| `view_image` | 看图 | 证据里可能需要 |
| `current_time` | 时间 | 低风险 |
| `get_context_remaining` | 上下文剩余量 | 帮助模型自我控制 |
| `mcp` / `mcp_resource` | 调 MCP 工具/资源 | 框架注入的证据查询、实验执行 |
| `dynamic` | 框架动态注入工具 | 可后置 |

内核保留 `update_plan`、`tool_search` 和多智能体工具；多模态上下文支持图片输入与 `view_image`。

### 3.2 MCP 工具

框架侧通过 MCP 提供证据查询、用例抽样、实验执行等工具。内核只负责：

- 连接 MCP server（HTTP/stdio，待定）。
- 拉取工具清单，转成 Responses 工具描述。
- 路由调用，把结果写回模型历史。
- 处理超时、错误、鉴权 token。

MCP server 本身在 rsi 框架（未来的 Rust 服务），不在内核。

### 3.3 工具可见性

- 工具面由会话配置、模型能力和工具注册结果决定，运行时工具更新遵循 Codex 的会话机制。
- 工具描述进入请求的 `tools` 字段；模型看不到未暴露的工具。
- 工具调用被拒绝时，返回结构化错误给模型，不 panic。

## 4. 预算

| 预算 | 语义 | 执行点 |
|---|---|---|
| `max_turns` | 模型采样轮数上限 | 回合循环 |
| `max_input_tokens` | 累计输入 token 上限 | 采样前估算 + 采样后账本 |
| `deadline_s` | 墙钟时间上限 | 回合循环 + 工具执行 |
| `max_tool_calls`（待定） | 工具调用次数上限 | 工具路由 |
| `max_output_tokens`（待定） | 单次/累计输出上限 | 请求参数 + 账本 |

到点行为：停止发起新的模型请求/工具调用，保留已产生的事件与历史，写一条终止事件，返回非零退出码（或 job 指定的错误码）。

## 5. 事件

### 5.1 用途

- 面板展示会话过程。
- 证据库记录“实际做了什么”。
- 成本核算（token、工具耗时、模型耗时）。
- 失败诊断（模型侧/基础设施/输入无效）。

### 5.2 草案事件类型

| 事件 | 关键字段 |
|---|---|
| `session.started` | session_id, job_id, stage, model, provider, workspace |
| `turn.started` | turn_id, index |
| `model.request` | model, input_tokens_estimate, tools, reasoning_effort |
| `model.response` | response_id, usage, duration_ms, finish_reason |
| `text.delta` | delta（可选，面板实时用） |
| `reasoning.delta` | delta（可选） |
| `tool.call` | tool_name, call_id, arguments（截断/脱敏） |
| `tool.result` | call_id, status, duration_ms, output（截断） |
| `compaction` | before/after tokens, reason |
| `budget.exceeded` | budget, limit, observed |
| `error` | class, message, retryable, http_status |
| `session.completed` | output_path, turns, usage, duration_ms |
| `session.failed` | reason, partial output |

字段命名、是否包含 `text.delta`、是否复用 OpenTelemetry 语义，待定。

### 5.3 与 codex 的关系

- codex 的 `protocol::EventMsg` 是内部事件模型，绑定了 app-server/TUI 的很多概念。
- 不建议把 `EventMsg` 直接暴露给 RSI 框架；建议定义一份更小的 rsi 事件 schema，内部从 `ResponseEvent`/工具结果映射。
- 如果需要复用 codex 的 `rollout` 写法，可以借鉴 JSONL/恢复逻辑，但字段独立。

## 6. 输出

- 结束时按 `output_schema` 校验结构化输出；校验失败视为会话失败，保留原始输出。
- 输出包含：结论/假设、证据引用、改动文件清单、自我批评、未决问题（具体 schema 由阶段决定）。
- 最终文本消息与结构化输出分开；结构化输出是权威，文本是给人看的。

## 7. 进程模型

设计文档 §6.5：

- rsi 框架用子进程启动内核，每个阶段一个进程、一次会话。
- 理由：上下文/成本可预测；阶段失败可单独重试；事件流按阶段切分；内核崩溃不带走框架。
- 调试终端可以连接独立 app-server；会话在线程运行期间保存在 Agent 进程中。

全 Rust 后的待定项：

- 仍然子进程，还是库调用 + 独立事件文件？
- 如果子进程：stdin 传 job、stdout 传结构化输出、文件传事件，还是全部走文件？
- 退出码约定：0 成功、2 预算超限、3 模型/网关失败、4 输出校验失败、5 内部错误（草案）。

建议：**保留子进程边界**，即使全 Rust。隔离、成本、重试都更简单；库调用可以作为测试/嵌入模式后加。

## 8. 阶段与工具差异

设计文档 §7 的九个阶段里，需要内核的是 `diagnose` 与 `propose`；其余是确定性框架代码。

| 阶段 | 是否需要内核 | 工具面 | 产出 |
|---|---|---|---|
| `sync` | 否 | — | 证据入库 |
| `measure` | 否 | — | 切片指标 |
| `record` | 否 | — | 诊断报告（不提案） |
| `diagnose` | 是 | 证据查询、用例抽样、读文件 | 带证据的假设 |
| `propose` | 是 | 上述 + `apply_patch`、写工作区 | 改动 + 自我批评 |
| `validate` | 否 | — | 合法/不合法 |
| `experiment` | 否 | — | 指标 |
| `adjudicate` | 否 | — | accept/reject/inconclusive |
| `deliver` | 否 | — | 分支/PR |
| `experience` | 否 | — | 经验条目 |
| `notify` | 否 | — | IM |

这意味着内核第一阶段不需要支持所有工具；`diagnose` 只需要只读工具 + MCP 证据查询，`propose` 才需要写文件。但内核的工具面要能按 job 配置，而不是编译期写死。

## 9. 模型

```toml
[model_providers.gateway]
name = "leihuo"
base_url = "https://ai-idc-inner.leihuo.netease.com/v1"
env_key = "LLM_API_KEY"
wire_api = "responses"
```

- 只支持 Responses，不做 Chat Completions 转换层。
- `store=false`（不把会话存在模型侧）。
- 流式 SSE。
- 工具使用 function/custom tool call。
- reasoning item 原样保留/回传，具体行为待网关验证。
